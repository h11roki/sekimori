# 2026-11 公開リポジトリのエージェントのワークフローの調査

ADR 0021 の決まりで、公開リポジトリのエージェントのワークフローに sekimori を当てた結果。件数と割合だけを書き、リポジトリの名前、パス、設定の抜き書きは載せない。

## 集め方

- 2026-11-13 に、GitHub のコード検索で `"uses: <Action>" path:.github/workflows` を検索した。Action ごとに、関連度の順で 100 件ずつ 10 ページまで取った
- リポジトリとパスで重複を除き、検索が返した blob の SHA で中身を取った
- 検査には、PR #15 をマージした後の main(`6626c90`、版は 0.1.0 のまま)を使った。ファイルごとに `--format sarif` で検査した

| Action | 検索の件数 | 集めたファイル | 読めたファイル | リポジトリ |
|---|---:|---:|---:|---:|
| claude-code-action | 23,456 | 673 | 668 | 656 |
| codex-action | 1,520 | 1,000 | 994 | 769 |
| run-gemini-cli | 371 | 392 | 382 | 279 |
| 合計 | | 2,065 | 2,044 | 1,685 |

- 読めなかった 21 ファイルは、YAML として壊れているか、`on:` の無いワークフローではないファイルか、`with:` に配列を渡すなど GitHub 自身も受け付けない書き方だった。割合の分母から除いた
- 1 つのワークフローが 2 つの Action を使うと、検索ではどちらかの Action に数えた。合計のリポジトリの数は重複を除いた数
- run-gemini-cli で検索の件数より集めたファイルが多いのは、ページを取る間に検索の結果が変わったため

## 結果

ファイルごとに、最も重い指摘で数えた。

| Action | error | warning だけ | 指摘あり |
|---|---:|---:|---:|
| claude-code-action | 2(0.3%) | 86(12.9%) | 88(13.2%) |
| codex-action | 1(0.1%) | 66(6.6%) | 67(6.7%) |
| run-gemini-cli | 52(13.6%) | 168(44.0%) | 220(57.6%) |
| 合計 | 55(2.7%) | 320(15.7%) | 375(18.3%) |

規則ごとの指摘の数(1 ファイルに複数ありうる)

| 規則 | error | warning |
|---|---:|---:|
| `broad-tools` | 59 | 383 |
| `unrestricted-trigger` | 59 | 63 |
| `other-secrets` | 0 | 50 |
| `long-lived-token` | 0 | 43 |
| `pr-head-checkout` | 0 | 2 |

- 3 つの軸が全て重なる `error` は、ほぼ run-gemini-cli に集まる。run-gemini-cli は起動できる人を自分では絞らず、常に `--yolo` で動くので、`if:` で起動した人を確かめず、`settings` で `tools.core` を絞らなければ、2 つの軸が満たされる
- claude-code-action と codex-action は、既定で書き込める人だけが起動できるので、`error` は `'*'` で開いた少数だけだった。`warning` の多くは、`--allowedTools "Bash"` や `--dangerously-skip-permissions`、codex の `danger-full-access` のような広い道具と、書き込みの権限の重なり

## 正誤の確かめ

ADR 0021 のとおり、無作為に選んだ指摘のワークフローを読んで確かめた。読んだのは、先入観を避けるため、判定の理由を知らない別のエージェント(Claude のサブエージェント)で、規則の説明と ADR だけを渡した。人が全てを読み直したものではない。

### 全ての指摘から 30 件(乱数の種 20261113)

手を入れる前の main(PR #13 の時点)の指摘から選んだ。

| 判定 | 件数 | 中身 |
|---|---:|---|
| 正しい | 23 | `broad-tools`、`long-lived-token`、`other-secrets` は、判断できたものが全て正しかった |
| 誤検知 | 3 | 全て workflow_run の `unrestricted-trigger`(`error`)。1 件は PR #14 で直した |
| 判断できない | 4 | 3 件は run-gemini-cli が作業場所の `.gemini/settings.json` を読む形で、`tools.core` がワークフローの外にある。1 件は `needs:` の前のジョブで絞る形 |

### `error` から 15 件(乱数の種 20261114)

`error` は見出しの数字になるので、別に確かめた。PR #14 の後の指摘から選んだ。15 件とも run-gemini-cli だった。

| 判定 | 件数 | 原因 |
|---|---:|---|
| 正しい | 7 | 起動した人を確かめない `issues` や `issue_comment` で、外部の人の本文がプロンプトに入る |
| 誤検知 | 8 | 下の表 |

| 誤検知の原因 | 件数 | その後 |
|---|---:|---|
| ラベルで絞っている | 3 | 付けたラベルの名前で絞る 2 件は、PR #15 で `warning` になった。今付いているラベルの一覧で絞る 1 件は残る(ADR 0023) |
| workflow_run の上流が `push: tags` だけ | 2 | 残る。上流は別のファイルにあり、1 つのファイルの検査では分からない(ADR 0022) |
| エージェントに外部の人の文面が届かない | 2 | 残る。`prompt` を渡していない、入力名を間違えている。起動はできても、指示を注入する経路が無い |
| `needs:` の前のジョブで絞っている | 1 | 残る(ADR 0012 の既知の制限) |

- 30 件と 15 件のどちらでも、`broad-tools` と、権限と秘密情報の軸の判定に誤りは見つからなかった。誤りは全て、起動できる人の軸だった
- 15 件のうち直した 2 件を除くと、残る 13 件の `error` のうち 6 件は誤検知の形になる。`error` の半分近くは、ワークフローの外(上流のファイル、前のジョブ、エージェントに渡す入力)を見ないと正しく判定できない
- 判定は少ない標本によるもので、割合の幅は大きい

## 上流のファイルを読んだ後(PR #19)

PR #19(ADR 0024)で、workflow_run の上流を、同じ検査に渡されたワークフローから名前で探すようにした。上の結果は 1 つのファイルずつ渡したもので、上流を探せない。そこで、同じリポジトリのファイルをまとめて渡して数え直した。

- 2 つ以上のファイルを集めた 230 リポジトリで、5 ファイルが `error` から `warning` になった。そのうち 2 件は、`error` の 15 件の確かめで誤検知とした、上流が `push: tags` だけで動く形
- これを反映すると、`error` のファイルは 55(2.7%)から 50(2.4%)、`warning` だけのファイルは 320 から 325 になる。指摘のあるファイルの数(375)は変わらない
- 集めたのはエージェントを使うファイルだけで、エージェントを使わない上流のファイルは集めていない。実際のリポジトリでディレクトリごとに検査すれば、さらに減る見込みがある

## プロンプトの無い run-gemini-cli を数えなくした後(PR #22)

PR #22(ADR 0025)で、`prompt` の入力を渡さない run-gemini-cli は、issue と discussion のイベントだけで動き、前のステップが既定のブランチの checkout だけなら、起動できる人の軸を数えないようにした。上と同じく、同じリポジトリのファイルをまとめて渡して数え直した。

- `error` のファイルは 50(2.4%)から 43(2.1%)になった。そのうち 2 件は、`error` の 15 件の確かめで、エージェントに外部の人の文面が届かない誤検知とした形
- 指摘のあるファイルは 375 から 367 になり、`warning` だけのファイルは 325 から 324 になった。起動できる人の軸の 0.5 が無くなり、合計が 2 を下回ったものは指摘が消えた
- 調査の全てのファイルで、`prompt` の無い run-gemini-cli のステップは 34 あった。`command`、`custom_prompt`、`prompt-file` のように、run-gemini-cli に無い名前の入力を渡しているものが含まれる

## `needs:` の前のジョブの `if:` を読んだ後(PR #25)

PR #25(ADR 0026)で、エージェントのジョブが `needs:` で待つ前のジョブの `if:` も、エージェントのステップの条件として読むようにした。上と同じく、同じリポジトリのファイルをまとめて渡して数え直した。

- 変わったのは 1 ファイルだけで、`warning` から指摘なしになった。`error` は 43 のまま、指摘のあるファイルは 367 から 366 になった
- 指摘が残るファイルのうち、エージェントのジョブが `needs:` で前のジョブを待つものは 50 あった。44 は、前のジョブのスクリプトが出力に結果を書き、エージェントのジョブの `if:` が `needs.<id>.outputs.<name>` と比べる形だった(`error` 4、`warning` 40)。1 はエージェントのジョブの `if:` に状態の関数があった。残る 5 は、前のジョブの `if:` を読んでも、指摘の重さが変わらなかった
- `error` の 15 件の確かめで `needs:` の形とした 1 件も、出力で絞る形だったので残る。この形は、スクリプトを読まないと判定できない(ADR 0026 のトレードオフ)

## エージェントの出力をコードに展開する規則を足した後(PR #30)

PR #30(ADR 0027)で、モデルの書いた文の出力(claude の `structured_output`、codex の `final-message`、gemini の `summary` と `error`)が、同じジョブの後の `run` か `actions/github-script` の `script` に `${{ }}` で展開される形を、道具の軸の規則 `agent-output-injection` として数えた。上と同じく、同じリポジトリのファイルをまとめて渡して数え直した。

- この形のファイルは 26 あり、新しい規則の指摘が出たのは 17(`error` 6、`warning` 11)。残る 9 は、他の軸が足りず指摘の重さに届かない
- 重さが変わったのは 1 ファイル(指摘なしから `warning`)。17 のほとんどは、すでに `broad-tools` で道具の軸を満たしていた。指摘のあるファイルは 366 から 367、`error` は 43 のまま
- 出力を `env` に入れて `$NAME` で読む安全な形は、同じジョブで 290 ファイル、ジョブの `outputs` で他のジョブに渡す形は 308 ファイルあった。他のジョブで `run` に展開する形は無く、github-script の `script` に展開する形が 1 あった(ADR 0027 のトレードオフ)

## エージェントが書き換えたコードを秘密情報で動かす規則を足した後(PR #33)

PR #33(ADR 0028)で、エージェントが作業場所を書き換えられ、同じジョブの後の `run` が秘密情報(`GITHUB_TOKEN` 以外)を持ってプロジェクトのコードを動かす形を、権限と秘密情報の軸の規則 `agent-code-with-secrets` として数えた。上と同じく、同じリポジトリのファイルをまとめて渡して数え直した。

- 新しい規則の指摘が出たのは 22 ファイルで、全て `warning`。重さが変わったのは 2 ファイル(指摘なしから `warning`)。指摘のあるファイルは 367 から 369、`error` は 43 のまま。多くは、すでに権限の軸(`permissions:` が無いなど)を満たしていた
- 当たったコマンドを見ながら、作業場所のファイルを動かさない形を除いた。ヒアドキュメントの本文の行も除いた。`perl -0pe` のようにフラグをまとめてその場のコードを渡す形、`node <<EOF` のようにワークフローに書いたスクリプトを渡す形、`$RUNNER_TEMP` や `/tmp` のスクリプト、拡張子の無い `/` を含む語(URL、`sed` の式、枝の名前)、レジストリの道具を動かす `npx`
- 残った指摘のコマンドは、作業場所の `.py`、`.mjs`、`.js`、`.sh` をインタプリタか直接で動かす形と、`npm install`、`npm run`、`python -m` だった

## v0.7.0 の指摘の正誤を確かめ直した結果(PR #36)

v0.7.0 で、同じリポジトリのファイルをまとめて渡したときの指摘から、乱数の種 20261115 で標本を選んだ。全ての指摘から 20 ファイル、新しい規則 `agent-output-injection` と `agent-code-with-secrets` の指摘からそれぞれ 10 ファイル。4 つの Claude のサブエージェントが、判定の基準(各軸の条件)と、ワークフローと sekimori の出力を読み、指摘ごとに正しい、誤検知、判断できないに分けた。判定者の結論は、各 Action のソースで確かめ直した。

| 標本 | 正しい | 誤検知 | 判断できない |
|---|---:|---:|---:|
| 全ての指摘から 20 | 18 | 1 | 1 |
| `agent-output-injection` から 10 | 9 | 0 | 1 |
| `agent-code-with-secrets` から 10 | 9 | 1 | 0 |

- 誤検知の 2 件
  - 全体の 1 件は、前のジョブのスクリプトが起動した人を確かめて出力に書き、エージェントのジョブの `if:` がそれと比べる形だった(ADR 0026 のトレードオフ)
  - `agent-code-with-secrets` の 1 件は、秘密情報を持つ後のステップの `if:` と、エージェントのステップの `if:` が、同じ値を別の定数と比べていて、同じ実行で両方は動かない形だった。sekimori はステップどうしの条件の矛盾を読まない
- 判断できない 2 件は、前のジョブのスクリプトの出力で絞る形と、issue のテンプレートが付けるかもしれないラベルで絞る形
- 判定者が誤検知とし、確かめ直して正しいとしたもの
  - Gemini CLI の古い設定の `coreTools`:v0.10 から v0.20 は `tools.core` に移し替えていたが、v0.30 以降のソースには無い。run-gemini-cli の既定は `latest` なので、道具は絞られない
  - `settings` に書いた Gemini の API キー:run-gemini-cli は `settings` を作業場所の `.gemini/settings.json` に書くので、エージェントが道具で読める。`env` のキーと違い、エージェントに届く秘密情報として数えるのは正しい
  - `Bash(python:*)` のようにインタプリタを前置きにした許可:何でも動かせるので広い道具とする(ADR 0013)
- 初めの 2 回の標本と違い、権限と秘密情報の軸にも誤検知が 1 件出た。新しい規則が後のステップを読むようになったため

PR #38(ADR 0030)で、エージェントのステップと、ジョブの中で変わらない値(`inputs`、`github`、`vars`、`needs`、`matrix`)について両立しない `if:` を持つ後のステップを、ADR 0027 と 0028 の規則で読まないようにした。

- v0.7.0 の確かめ直しで誤検知とした 1 件は、指摘が消えた
- 調査のデータでは、1 ファイルが `warning` から指摘なしになった。`agent-code-with-secrets` の指摘は 22 から 21 ファイル、指摘のあるファイルは 369 から 368

## Claude Code の base action の調査(PR #46)

v0.9.0 で base action に対応した(ADR 0032)ので、同じ取り方で集め直した。

- GitHub のコード検索で、`uses: anthropics/claude-code-base-action` と `uses: anthropics/claude-code-action/base-action` を検索した。449 ファイル(292 リポジトリ)で、前者が 398、後者が 51
- v0.9.0 で、同じリポジトリのファイルをまとめて渡して検査した。指摘のあるファイルは 98(21.8%)、`error` は 9(2.0%)

| 規則 | ファイル |
|---|---:|
| `broad-tools` | 77 |
| `unrestricted-trigger` | 34(`error` 9) |
| `other-secrets` | 9 |
| `long-lived-token` | 5 |
| `pr-head-checkout` | 2 |

- 正誤の確かめ:`error` の 9 件の全てと、`warning` から乱数の種 20261116 で選んだ 11 件を、2 つの Claude のサブエージェントが判定した

## 偏りと限り

- コード検索の関連度の順に取ったので、無作為の標本ではない。claude-code-action は、検索の件数の約 3% しか見ていない
- 検索した時点のファイルなので、その後に直されたワークフローも数えている
- fork のリポジトリは、検索の対象に入らない
- 正誤の確かめは、Claude のサブエージェントが読んだもので、標本も 3 回で合わせて 85 件と少ない
- 指摘のあったリポジトリの持ち主には、知らせていない(ADR 0021)

## 数え直し方

- 上の検索と取り方で集め、`sekimori --format sarif <ファイル>` をファイルごとに流して、`runs[0].results` の `ruleId` と `level` を数える
- 集めたファイルと、集める道具は、他人のコードなのでリポジトリに入れていない
