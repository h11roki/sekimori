# 2026-11 公開リポジトリのエージェントのワークフローの調査

ADR 0021 の決まりで、公開リポジトリのエージェントのワークフローに sekimori を当てた結果。件数と割合だけを書き、リポジトリの名前、パス、設定の抜き書きは載せない。

## 集め方

- 2026-11-13 に、GitHub のコード検索で `"uses: <Action>" path:.github/workflows` を検索した。Action ごとに、関連度の順で 100 件ずつ 10 ページまで取った
- リポジトリとパスで重複を除き、検索が返した blob の SHA で中身を取った
- 検査には、PR #15 をマージした後の main(`6626c90`、版は 0.1.0 のまま)を使った。ファイルごとに `--format sarif` で検査した

| Action | 検索の件数 | 集めたファイル | 読めたファイル | リポジトリ |
|---|---:|---:|---:|---:|
| claude-code-action | 23,456 | 673 | 668 | 656 |
| codex-action | 1,520 | 1,000 | 994 | 769 |
| run-gemini-cli | 371 | 392 | 382 | 279 |
| 合計 | | 2,065 | 2,044 | 1,685 |

- 読めなかった 21 ファイルは、YAML として壊れているか、`on:` の無いワークフローではないファイルか、`with:` に配列を渡すなど GitHub 自身も受け付けない書き方だった。割合の分母から除いた
- 1 つのワークフローが 2 つの Action を使うと、検索ではどちらかの Action に数えた。合計のリポジトリの数は重複を除いた数
- run-gemini-cli で検索の件数より集めたファイルが多いのは、ページを取る間に検索の結果が変わったため

## 結果

ファイルごとに、最も重い指摘で数えた。

| Action | error | warning だけ | 指摘あり |
|---|---:|---:|---:|
| claude-code-action | 2(0.3%) | 86(12.9%) | 88(13.2%) |
| codex-action | 1(0.1%) | 66(6.6%) | 67(6.7%) |
| run-gemini-cli | 52(13.6%) | 168(44.0%) | 220(57.6%) |
| 合計 | 55(2.7%) | 320(15.7%) | 375(18.3%) |

規則ごとの指摘の数(1 ファイルに複数ありうる)

| 規則 | error | warning |
|---|---:|---:|
| `broad-tools` | 59 | 383 |
| `unrestricted-trigger` | 59 | 63 |
| `other-secrets` | 0 | 50 |
| `long-lived-token` | 0 | 43 |
| `pr-head-checkout` | 0 | 2 |

- 3 つの軸が全て重なる `error` は、ほぼ run-gemini-cli に集まる。run-gemini-cli は起動できる人を自分では絞らず、常に `--yolo` で動くので、`if:` で起動した人を確かめず、`settings` で `tools.core` を絞らなければ、2 つの軸が満たされる
- claude-code-action と codex-action は、既定で書き込める人だけが起動できるので、`error` は `'*'` で開いた少数だけだった。`warning` の多くは、`--allowedTools "Bash"` や `--dangerously-skip-permissions`、codex の `danger-full-access` のような広い道具と、書き込みの権限の重なり

## 正誤の確かめ

ADR 0021 のとおり、無作為に選んだ指摘のワークフローを読んで確かめた。読んだのは、先入観を避けるため、判定の理由を知らない別のエージェント(Claude のサブエージェント)で、規則の説明と ADR だけを渡した。人が全てを読み直したものではない。

### 全ての指摘から 30 件(乱数の種 20261113)

手を入れる前の main(PR #13 の時点)の指摘から選んだ。

| 判定 | 件数 | 中身 |
|---|---:|---|
| 正しい | 23 | `broad-tools`、`long-lived-token`、`other-secrets` は、判断できたものが全て正しかった |
| 誤検知 | 3 | 全て workflow_run の `unrestricted-trigger`(`error`)。1 件は PR #14 で直した |
| 判断できない | 4 | 3 件は run-gemini-cli が作業場所の `.gemini/settings.json` を読む形で、`tools.core` がワークフローの外にある。1 件は `needs:` の前のジョブで絞る形 |

### `error` から 15 件(乱数の種 20261114)

`error` は見出しの数字になるので、別に確かめた。PR #14 の後の指摘から選んだ。15 件とも run-gemini-cli だった。

| 判定 | 件数 | 原因 |
|---|---:|---|
| 正しい | 7 | 起動した人を確かめない `issues` や `issue_comment` で、外部の人の本文がプロンプトに入る |
| 誤検知 | 8 | 下の表 |

| 誤検知の原因 | 件数 | その後 |
|---|---:|---|
| ラベルで絞っている | 3 | 付けたラベルの名前で絞る 2 件は、PR #15 で `warning` になった。今付いているラベルの一覧で絞る 1 件は残る(ADR 0023) |
| workflow_run の上流が `push: tags` だけ | 2 | 残る。上流は別のファイルにあり、1 つのファイルの検査では分からない(ADR 0022) |
| エージェントに外部の人の文面が届かない | 2 | 残る。`prompt` を渡していない、入力名を間違えている。起動はできても、指示を注入する経路が無い |
| `needs:` の前のジョブで絞っている | 1 | 残る(ADR 0012 の既知の制限) |

- 30 件と 15 件のどちらでも、`broad-tools` と、権限と秘密情報の軸の判定に誤りは見つからなかった。誤りは全て、起動できる人の軸だった
- 15 件のうち直した 2 件を除くと、残る 13 件の `error` のうち 6 件は誤検知の形になる。`error` の半分近くは、ワークフローの外(上流のファイル、前のジョブ、エージェントに渡す入力)を見ないと正しく判定できない
- 判定は少ない標本によるもので、割合の幅は大きい

## 上流のファイルを読んだ後(PR #19)

PR #19(ADR 0024)で、workflow_run の上流を、同じ検査に渡されたワークフローから名前で探すようにした。上の結果は 1 つのファイルずつ渡したもので、上流を探せない。そこで、同じリポジトリのファイルをまとめて渡して数え直した。

- 2 つ以上のファイルを集めた 230 リポジトリで、5 ファイルが `error` から `warning` になった。そのうち 2 件は、`error` の 15 件の確かめで誤検知とした、上流が `push: tags` だけで動く形
- これを反映すると、`error` のファイルは 55(2.7%)から 50(2.4%)、`warning` だけのファイルは 320 から 325 になる。指摘のあるファイルの数(375)は変わらない
- 集めたのはエージェントを使うファイルだけで、エージェントを使わない上流のファイルは集めていない。実際のリポジトリでディレクトリごとに検査すれば、さらに減る見込みがある

## プロンプトの無い run-gemini-cli を数えなくした後(PR #22)

PR #22(ADR 0025)で、`prompt` の入力を渡さない run-gemini-cli は、前のステップで PR の head を checkout していなければ、起動できる人の軸を数えないようにした。上と同じく、同じリポジトリのファイルをまとめて渡して数え直した。

- `error` のファイルは 50(2.4%)から 41(2.0%)になった。そのうち 2 件は、`error` の 15 件の確かめで、エージェントに外部の人の文面が届かない誤検知とした形
- 指摘のあるファイルは 375 から 365 になり、`warning` だけのファイルは 325 から 324 になった。起動できる人の軸の 0.5 が無くなり、合計が 2 を下回ったものは指摘が消えた
- 調査の全てのファイルで、`prompt` の無い run-gemini-cli のステップは 34 あった。`command`、`custom_prompt`、`prompt-file` のように、run-gemini-cli に無い名前の入力を渡しているものが含まれる

## 偏りと限り

- コード検索の関連度の順に取ったので、無作為の標本ではない。claude-code-action は、検索の件数の約 3% しか見ていない
- 検索した時点のファイルなので、その後に直されたワークフローも数えている
- fork のリポジトリは、検索の対象に入らない
- 正誤の確かめは、Claude のサブエージェントが読んだもので、標本も 45 件と少ない
- 指摘のあったリポジトリの持ち主には、知らせていない(ADR 0021)

## 数え直し方

- 上の検索と取り方で集め、`sekimori --format sarif <ファイル>` をファイルごとに流して、`runs[0].results` の `ruleId` と `level` を数える
- 集めたファイルと、集める道具は、他人のコードなのでリポジトリに入れていない
