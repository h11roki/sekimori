# 0038. 書きかけの SARIF のファイルは消し、書けなかったことは `--format github` で注釈にする

- ステータス: 承認
- 日付: 2026-11-15

## 文脈

- ADR 0037 で、次の 2 つをトレードオフとして受け入れた
  - 書いている途中で失敗した SARIF のファイルが残る。Action はファイルがあれば `sarif-file` を出すので、送るステップが JSON の誤りで落ち、本当の原因が隠れる
  - `--sarif-file` や `--summary-file` を書けなかったことは標準エラー出力にだけ出て、`--format github` でも注釈にならない。Action の画面には「終了コード 2」しか出ない
- 読めないワークフローは、`--format github` では注釈にしている(ADR 0035)

## 検討した選択肢

1. SARIF は同じディレクトリの一時ファイルに書き、書き終えてから名前を変える
2. SARIF のファイルが書けなかったら、それが普通のファイルなら消す
3. 今のまま

どの案でも、ファイルが書けなかったことは、`--format github` では `::error` の注釈にする。

## 決定

高橋さんが判断を任せ(2026-11-15 に「止まらないで。開発改善を進めて」)、Claude が 2 を選んだ。最初は 1 で実装したが、PR #58 のレビューで次の問題が分かり、2 に変えた。

- 普通のファイルなら、書けなかったときに消す。消せなければ、それも出す
- 書けなかったことの注釈は `file` を付けない(ワークフローのファイルの指摘ではないため)。注釈を標準出力に書けなければ、その理由と元のエラーを標準エラー出力に出す

## 理由

- 1 は、`/dev/stdout` や `>(jq ...)` のようなパイプ、名前付きパイプに書けなくなる(隣に一時ファイルを作れない)。シンボリックリンクは先のファイルでなくリンクが置き換わり、権限やハードリンクも失う。一時ファイルの名前が決まっていると、同時に動く 2 つの実行がぶつかる
- `fs::write` は書く前にファイルを空にするので、失敗したときに前の実行の SARIF は残っていない。消せば、書きかけの SARIF が送られることも、古い SARIF が新しい結果として送られることもない
- 注釈にすれば、Action の画面で、何が書けなかったかが分かる

## 受け入れたトレードオフ

- 書けなかった SARIF を消せなかったときは、書きかけのファイルが残る。そのときは消せなかったことも出す
- シンボリックリンクの先が普通のファイルなら、消えるのはリンクで、書きかけの先のファイルは残る
