# 0031. 指摘は、その行かエージェントのステップの行の `# sekimori: ignore[規則]` のコメントで抑える

- ステータス: 承認
- 日付: 2026-11-15

## 文脈

- sekimori は指摘があると終了コード 1 を返し、Action のステップも失敗する(ADR 0010、0017)。危険を承知した上で動かしているワークフローでも、指摘を消す手段が無い。CI に入れると止まり続けるので、使い続けてもらえない
- zizmor は、指摘の行に `# zizmor: ignore[規則]` と書くと、その指摘を抑える。同じ利用者が両方を使うことが多い
- yamlpath の `Document` は、元の文と、ある位置がコメントの中かを返せる

## 検討した選択肢

1. 行に書くコメント `# sekimori: ignore[規則, ...]` で抑える。指摘が指す行か、エージェントのステップの行(`uses:` の行)に書く
2. 設定ファイル(`.github/sekimori.yml` など)に、ファイルと規則を並べる
3. CLI と Action の入力で、規則を丸ごと外す

## 決定

高橋さんが判断を任せ(2026-11-15 に「止まらないで。開発改善を進めて」)、Claude が 1 を選んだ。

- 書き方は `# sekimori: ignore[規則の ID]`。カンマで区切って複数の規則を書ける。`# sekimori: ignore` だけなら、その行の全ての規則を抑える
- 置き場所は、指摘が指す位置の行か、エージェントのステップの `uses:` の行。エージェントのステップの行に書けば、そのステップの指摘をまとめて抑える
- コメントは、yamlpath がコメントと認めるものだけ読む。文字列の中の `#` は読まない
- 抑えた指摘は、平文にも SARIF にも出さず、終了コードにも数えない
- 軸の重さは変えない。抑えるのは、その規則の指摘だけ。同じステップの他の規則は、これまでどおりの重さで出る
- 知らない規則の ID は、何も抑えない

## 理由

- 抑える理由がワークフローの隣に残り、PR のレビューで見える(選択肢 2 は、離れたファイルで抑えるので見落としやすい)
- zizmor と同じ書き方なので、覚えることが少ない
- 規則を丸ごと外すと、新しく足したワークフローの同じ危険も見逃す(選択肢 3)
- 重さを変えないので、抑えたことで他の規則の判定が軽くならない

## 受け入れたトレードオフ

- 抑えた数は表示しない。抑えたことは、コメントとしてワークフローに残る
- SARIF の `suppressions` は使わず、結果から外す。コードスキャンに抑えた指摘を残したいときは、コードスキャンの画面で閉じる
- `# sekimori: ignore` の打ち間違い(`ignroe` など)は、警告せずに読まない

## 再検討する条件

- 抑えた指摘を後から見直したいという要望が出たとき(SARIF の `suppressions` に移す)
