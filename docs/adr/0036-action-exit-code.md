# 0036. Action は sekimori の終了コードを `exit-code` の出力に出し、Action を試すジョブはそれが 1 であることを確かめる

- ステータス: 承認(`exit-code` は 1 回の実行の終了コードになり、要約が書けないときの扱いと `sarif-file` を出す条件は 0037 で置き換え。試すジョブの注釈の確かめは 0046 で足した)
- 日付: 2026-11-15

## 文脈

- Action を試すジョブ(ADR 0019)は、指摘のあるワークフローで Action を動かし、ステップが失敗したことと SARIF の中身を確かめる
- PR #49 で、Action の `action.yml` を `--format github` に切り替えたところ、Action はリリース済みの v0.10.0 のバイナリを使うので、知らない引数で終了コード 2 で落ちた。ステップが失敗したことしか見ていなかったので、このジョブは通った
- sekimori の終了コードは、0 が指摘なし、1 が指摘あり、2 が読めないファイルか引数の誤り(ADR 0010)。Action の利用者からは、ステップの成否しか見えず、1 と 2 を区別できない

## 検討した選択肢

1. Action の出力 `exit-code` に sekimori の終了コードを出し、Action を試すジョブは `exit-code` が `1` であることを確かめる
2. Action を試すジョブで、ジョブの要約やログを読んで確かめる
3. 何もしない

## 決定

高橋さんが判断を任せ(2026-11-15 に「止まらないで。開発改善を進めて」)、Claude が 1 を選んだ。

- `exit-code` は、注釈の実行と SARIF の実行の終了コードの大きい方(ステップの終了コードと同じ)。sekimori が落ちたときは 0、1、2 以外の値もそのまま出す。ジョブの要約が書けなくても、`sarif-file` と `exit-code` は出し、要約が書けなかったことを注釈で警告する
- Action を試すジョブは、`outcome` が `failure` で、`exit-code` が `1` であることを確かめる

## 理由

- 指摘があったことと、sekimori が動けなかったことを、試すジョブで区別できる
- 利用者も、`continue-on-error: true` と組み合わせれば、指摘のときだけ先に進むといった使い分けができる
- 要約は別のステップから読めず、ログを読むには API と権限が要る(選択肢 2)

## 受け入れたトレードオフ

- Action の出力が 1 つ増え、終了コードの意味が Action の約束になる
