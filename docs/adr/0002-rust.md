# 0002. Rust で書く

- ステータス: 承認
- 日付: 2026-11-08

## 文脈

- sekimori は、ワークフローの YAML を読んで規則で判定する CLI と、それを包む GitHub Action(ADR 0001)
- 作り手が主に書く言語は Python
- GitHub Actions の静的検査の定番の zizmor は Rust で書かれている。ADR 0001 は、zizmor が同じ検査を出したら規則を寄稿して畳む道を残している
- GitHub Action の作り方は、JavaScript(TypeScript)、Docker、複合(composite)の 3 つ。Python や Rust で書いたものは、Docker か、実行ファイルを取ってくる複合の Action で包む

## 検討した選択肢

1. Python。書き慣れていて、行番号つきで YAML を読めるライブラリ(ruamel.yaml)がある。uvx や pip で CLI を配れる。Action にすると Python の準備のぶん数秒遅く、zizmor に寄稿するときは書き直しになる
2. TypeScript。Action の標準の言語で一番速く動き、npm でも配れる。主に書く言語ではなく、組み立てたもの(dist)をリポジトリに含めるなど、Action 特有の手間がある
3. Rust。zizmor と同じ言語で寄稿の道が近く、単一の実行ファイルで速い。覚える手間が大きく、一人で 3 か月で最初の版を出すには重い

## 決定

高橋さんが 3 を選んだ。

- 安定版のツールチェーンを rustup で入れて使う(2026-11-08 時点で 1.99.1)
- YAML を行番号つきで読むクレートの選び方と、Action での配り方(実行ファイルを Releases から取るか、Docker か)は、実装の前に別の ADR で決める

## 理由

- zizmor と同じ言語なら、規則を寄稿するときに書き直さずに済み、zizmor の作り(YAML の位置の扱い、SARIF の出力)からも学べる
- 単一の実行ファイルなので、CI で準備の時間がかからず、使う人の環境に言語の処理系を求めない

## 受け入れたトレードオフ

- Rust を覚える手間で、最初の版が遅れる。最初の版の規則を 5 個ほどに絞り(ADR 0003)、範囲を小さく保つ
- 作り手が書き慣れていない言語なので、慣用から外れた書き方が残りやすい。CI で clippy と rustfmt を流す

## 再検討する条件

- 最初の版(公式の 3 つの Action、規則 5 個ほど)を 3 か月で出せる見込みが立たないとき
