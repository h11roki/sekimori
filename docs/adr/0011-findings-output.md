# 0011. 指摘は規則の ID と位置と軸の内訳で出し、軸の値は半分を単位に数える

- ステータス: 承認
- 日付: 2026-11-12

## 文脈

- ADR 0007 は、エージェントのステップごとに 3 つの軸の値(起動できる人は 1、0.5、0、他の 2 つは 1 か 0)を足し、3 で `error`、2 以上で `warning` とした。指摘は当たった規則ごとに出し、満たした軸とその理由になった設定を書く
- ADR 0009 は、各社の設定を軸の事実に写す段と、規則と重さの段と、出す段を分けた。ADR 0010 は、出力を英語にし、指摘があれば終了コード 1 とした
- SARIF の結果は、規則の ID(`ruleId`)と位置(行と列)を持つ。GitHub のコードスキャンは、この ID で指摘を見分ける
- コンパイラや多くの lint は、`パス:行:列: 重さ: 文` の 1 行で指摘を出す。エディタや CI のログから、その位置に飛べる

## 検討した選択肢

1. 1 行目をコンパイラと同じ形(`パス:行:列: 重さ[規則の ID]: 文`)にし、続く字下げした行に 3 つの軸の値と理由、合計を書く
2. 1 行だけにし、軸の内訳は書かない
3. 規則ごとではなく、エージェントのステップごとに 1 つの指摘にまとめる

## 決定

高橋さんが判断を任せ(2026-11-12 に「承認取らなくていい」)、Claude が 1 を選んだ。

- 規則の ID は英語の kebab-case にする。ADR 0006 の 5 つの規則は、起動の制限を外したが `unrestricted-trigger`、広い道具が `broad-tools`、期限の無いトークンが `long-lived-token`、PR の head の checkout が `pr-head-checkout`、他の秘密情報が `other-secrets`
- 平文の出力は次の形にする。位置は、理由になった設定の行と列(1 から数える)。位置を引けないときは、指摘を落とさずにファイルの先頭(1:1)を指す

  ```text
  .github/workflows/claude.yml:14:11: warning[unrestricted-trigger]: anthropics/claude-code-action@v1 in job `claude` can be started by anyone
    who can trigger      1    allowed_non_write_users: '*', on issue_comment
    allowed tools        0
    permissions/secrets  1    no permissions are set, so GITHUB_TOKEN gets the repository default
    total                2 of 3
  ```

- 軸の値は、半分を 1 とした整数で持つ(1 は 2、0.5 は 1)。浮動小数点の足し算と比べを避けるため。表示するときに 0.5 単位に戻す
- 軸の値と理由は、各社の設定を写した事実から規則の段で決める。各社の入力の名前を知るのは写す段だけで、規則の段は「起動の制限が外れているか」のような 3 社に共通の事実だけを見る
- 指摘はファイルごとに、エージェントのステップの順、その中では当たった規則の順に出す

## 理由

- 1 行目がコンパイラと同じ形なので、エディタや CI のログから位置に飛べ、`grep` で数えられる。規則の ID は SARIF の `ruleId` にそのまま使える
- ADR 0001 の考え(1 つの設定ではなく、3 つの軸の重なりで判断する)は、内訳を見ないと伝わらない。2 では、なぜ `warning` で `error` でないのかが分からない
- 3 では、規則ごとに位置が違うのを 1 つの位置にまとめることになり、SARIF で直す場所を指せない

## 受け入れたトレードオフ

- 1 つのステップで規則が 2 つ当たると、軸の内訳が 2 度出る
- 出力の形は機械向けには決めていない。機械で読む人には SARIF を使ってもらう

## 再検討する条件

- 1 つのステップで複数の規則が当たる例が多く、出力が長すぎるとき
- 利用者から、JSON などの機械向けの平文を求められたとき
