# 0046. Action を試すジョブの後に、そのジョブの注釈を API で読み、SARIF と突き合わせる

- ステータス: 承認
- 日付: 2026-11-17

## 文脈

- Action は注釈、SARIF、ジョブの要約の 3 つを 1 回の実行で出す(ADR 0035、0037)。Action を試すジョブ(ADR 0019、0036)が確かめているのは、ステップの失敗、`exit-code` が 1 であること、SARIF の中身だけ
- 注釈は sekimori の標準出力に出るワークフローコマンドで、出力には残らない。注釈の形が壊れても(`file=` が絶対パスになる、`title` が抜けるなど)、試すジョブは通る
- 2026-11-17 に試したところ、check run の注釈の API(`GET /repos/{owner}/{repo}/check-runs/{id}/annotations`)は、ジョブが走っている間は空を返し、ジョブが終わった後は sekimori の注釈を `path`、`start_line`、`annotation_level`、`title` 付きで返した
- ジョブの要約は API で読めない

## 検討した選択肢

1. `action` のジョブの後に、`needs: action` で別のジョブを動かし、`action` のジョブの注釈を API で読んで、SARIF から作った期待値と突き合わせる
2. Action を試すジョブの中で、注釈を API で読む
3. Action を試すジョブの中で、バイナリを `--format github` でもう一度動かし、標準出力を確かめる
4. 何もしない

## 決定

高橋さんが判断を任せ(2026-11-17 に「進めて」)、Claude が 1 を選んだ。

- `action` のジョブは、SARIF の結果ごとに `[path, 行, 列, 重さ, 題, 本文]` を作り、重複を除いて並べた JSON をジョブの出力に出す。重さは注釈の `annotation_level` に合わせ、`error` を `failure`、`note` を `notice` にする。題は `sekimori <規則の ID>`。重さごとに 10 件を超えるときは、そのことを注釈で示して落ちる
- 新しいジョブ `action-annotations` は、`checks: read` と `actions: read` で、同じ run の `action` のジョブを `filter=latest` で探す(失敗したジョブだけをやり直したときも見つかるように)。ちょうど 1 つ見つからなければ落ちる
- その注釈のうち、題が `sekimori` か `sekimori ` で始まるものを同じ形に並べて、期待値と一致することを確かめる。題が `sekimori` だけの注釈(読めないファイルや書けない出力の知らせ)は期待値に無いので、出れば落ちる
- 注釈がまだ読めないときに備え、空のあいだは 5 秒おきに 6 回まで読み直す
- Action を動かさなかったとき(版がまだリリースされていないとき)は、新しいジョブも飛ばす

## 理由

- 注釈は利用者が PR の画面で最初に見る結果で、ここが壊れると気づきにくい
- 2 は試したとおり、走っている間は注釈が読めない
- 3 は Action の中で動いた実行ではなく、別の実行を確かめることになる
- SARIF と突き合わせれば、注釈が結果の数、ファイル、行、列、重さ、規則、本文のどれかで食い違ったときに落ちる

## 受け入れたトレードオフ

- ジョブが 1 つ増え、`action` のジョブに `checks: read` は要らないが、新しいジョブには `checks: read` と `actions: read` が要る
- GitHub は 1 つのステップの注釈を種類ごとに 10 件までしか出さないので、試す fixture の指摘は重さごとに 10 件以下に保つ
- SARIF は同じ規則で同じ位置の指摘を 1 つの結果にまとめ(ADR 0018)、重さはまとめた中で最も重いものになる。注釈は指摘ごとに出るので、まとめた指摘の重さが違う fixture では一致しない。今の fixture にはまとまる指摘が無い
- ジョブの要約は確かめられない。要約の中身は Rust のテストで確かめる
