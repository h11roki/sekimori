# 0029. エージェントの後の push、マージ、公開は、規則にしない

- ステータス: 承認
- 日付: 2026-11-15

## 文脈

- 本人に次の作業を聞き、2026-11-15 に「エージェントの後の push の規則を調べる」が選ばれた
- 調査のデータ(ADR 0021)で、エージェントと同じジョブの後のステップを数えた。エージェントのジョブを持つファイルのうち、次の形があった
  - `git push` が 236、PR を作るのが 209(`gh pr create` か `peter-evans/create-pull-request`)
  - 既定の枝か今の枝へそのまま push するのが 33
  - リリースや公開(`gh release create`、`npm publish` など)が 16
  - `gh pr merge` が 13(うち `--auto` が 7)
- どの形も、ジョブのトークンかエージェントの外の秘密情報に書き込みの権限が要る。`GITHUB_TOKEN` の書き込みは、権限と秘密情報の軸ですでに数えている(ADR 0007)。保存した秘密情報のトークンは `long-lived-token` と `agent-code-with-secrets` で数える
- 既定の枝に書き込めるか、マージに人の承認が要るかは、枝の保護とリポジトリのルールセットで決まる。これらはワークフローのファイルの外にある

## 検討した選択肢

1. 規則にしない。調べた数と理由を残す
2. 重さは変えず、権限と秘密情報の軸の理由に「後のステップが既定の枝に push する」などを書き足す
3. 新しい規則として、権限と秘密情報の軸を満たす

## 決定

高橋さんが選んだ(2026-11-15)。1 にする。

## 理由

- 3 は、すでに書き込みの権限で満たしている軸を、同じ理由でもう一度満たすだけで、重さはほとんど変わらない。枝の保護で止まる push やマージも数えるので、誤検知を増やす
- 2 は直す人の手がかりにはなるが、枝の保護を読めない以上、「人の確認が飛ばされる」とは言い切れない。実装とレビューの手間に見合わない
- 調べた数と理由を残せば、同じ検討を繰り返さずに済み、README の規則の範囲の説明にもなる

## 受け入れたトレードオフ

- 枝の保護が無いリポジトリで、エージェントの変更がそのまま既定の枝やリリースに入る形を、規則として名指ししない。権限の軸の重さには入っている
- `gh pr merge --auto` や `--admin` のように、保護を前提にした回り道も、特に扱わない

## 再検討する条件

- 枝の保護やルールセットを読める入力(GitHub の API など)を sekimori に足すとき
- エージェントの変更をそのまま公開する形の事件や報告が出たとき
