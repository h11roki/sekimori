# 0010. CLI はパスを受け取り、読めないファイルがあっても残りを検査し、終了コードを 0、1、2 に分け、英語で出す

- ステータス: 承認
- 日付: 2026-11-12

## 文脈

- ADR 0001 は、CLI と GitHub Action で配り、SARIF で GitHub のコードスキャンに出すと決めた。使う人は、AI エージェントを CI で動かす OSS のメンテナーと、企業のプラットフォームやセキュリティの担当者
- GitHub は、ワークフローを `.github/workflows` の直下の `.yml` と `.yaml` から読む
- CI で使うときは、終了コードで後の段を止めるかを決める。SARIF をコードスキャンに上げるときは、終了コードで止めず、GitHub の側で PR を止められる

## 検討した選択肢

1. パスを受け取る(無ければ `.github/workflows`)。読めないファイルがあっても残りを検査する。終了コードは、0 が指摘なし、1 が指摘あり、2 が読めないファイルか引数の誤り
2. 1 と同じで、読めないファイルがあればそこで止める
3. 1 と同じで、終了コードを重さごとに分ける(`warning` と `error` で別の値)

## 決定

高橋さんが判断を任せ(2026-11-12 に「承認取らなくていい」)、Claude が 1 を選んだ。

- 引数はファイルかディレクトリのパスで、いくつでも渡せる。ディレクトリなら直下の `.yml` と `.yaml`(大文字と小文字は区別しない)を名前の順に読み、下の階層は見ない。1 つも無いディレクトリは、何も検査せずに 0 で終わらないよう、引数の誤りとして扱う。ファイルなら拡張子を問わずに読む
- ファイルとそのディレクトリの両方を渡すなどして同じファイルに 2 度たどり着いても、検査は 1 度だけにする
- 読めないファイルは標準エラーに出して、残りを検査する
- 終了コードは、0 が指摘なし、1 が `warning` 以上の指摘あり、2 が読めないファイルか引数の誤り。読めないファイルがあれば、指摘があっても 2 にする(結果が欠けているため)
- 出力の言葉は英語にする。ADR とコミットメッセージは日本語のまま
- 引数の解析は clap(derive)を使う

## 理由

- 1 つの壊れたファイルで、他のワークフローの指摘が隠れない
- 重さは出力に書いてあり、CI では 0 以外で止めれば足りる。コードスキャンに上げる使い方では、そもそも終了コードを使わない
- 使う人が世界にいるので、出力は英語にする
- clap は Rust の CLI で最も使われていて、zizmor も使っている。引数と `--help` と `--version` を型から作れる

## 受け入れたトレードオフ

- 日本語の利用者には出力が読みにくい
- 終了コードだけでは `error` と `warning` を区別できない
- clap のぶん、ビルドの時間と実行ファイルが大きくなる

## 再検討する条件

- 利用者から、終了コードで重さを分けたいと求められたとき
- 日本語の出力を求められたとき
