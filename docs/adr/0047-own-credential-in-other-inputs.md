# 0047. エージェントの資格情報の入力に渡した秘密情報は、他の入力や env にあっても他の秘密情報として数えない

- ステータス: 承認
- 日付: 2026-11-19

## 文脈

- ADR 0006 と 0015 は、エージェント自身の資格情報を `other-secrets` で数えないと決めた。エージェントが読めるかどうかに関わらず数えない(codex-action の `env` の `OPENAI_API_KEY` はシェルから読めるが、数えない)
- 0015 は資格情報を、入力の名前(`gemini_api_key` など、エージェントに届く入力の一覧に入れない)と `env` の名前(`GEMINI_API_KEY` など)で見分ける。同じ秘密情報を、エージェントに届く別の入力や、名前の違う `env` に置いたときは見分けない
- 2026-11-19 に、v0.16.0 の公開ワークフローの指摘から 30 ファイルを選んで正誤を確かめたところ、誤検知の 5 件のうち 2 件がこの形だった。run-gemini-cli の `gemini_api_key` に渡した `secrets.GEMINI_API_KEY` を、`settings` の `mcpServers` の画像生成の MCP サーバーの `env` にも書いていた
- v0.7.0 の確かめ(PR #36)では、`settings` に書いた Gemini の API キーを、エージェントが `.gemini/settings.json` から読めるので数えるのは正しいとした。この判断は、読めても自身の資格情報は数えないという 0015 のトレードオフと食い違っていた
- 各 Action の資格情報の入力(2026-11-19 に各リポジトリの既定の枝の `action.yml` で確かめた)
  - claude-code-action と base action: `anthropic_api_key`、`claude_code_oauth_token`
  - codex-action: `openai-api-key`
  - run-gemini-cli: `gemini_api_key`、`google_api_key`

## 検討した選択肢

1. 資格情報の入力か資格情報の `env` に渡した秘密情報と同じ `secrets.*` は、エージェントに届く他の入力や `env` にあっても `other-secrets` で数えない
2. 秘密情報の名前が資格情報の `env` の名前(`GEMINI_API_KEY` など)と同じなら数えない
3. 今のまま、資格情報の入力の外に書いたものは数える

## 決定

高橋さんが判断を任せ(2026-11-19 に「改善して」)、Claude が 1 を選んだ。

- claude では資格情報の入力と、資格情報の名前の `env`(0015 の一覧)の値から、gemini では資格情報の入力の値から、式に流れ込む `secrets.*` を全て集める。`secrets` をまるごと渡すものは集めない
  - run-gemini-cli は `GEMINI_API_KEY` と `GOOGLE_API_KEY` を入力の値で上書きするので、呼び出し側の `env` のその名前は資格情報にならない
  - base action も `ANTHROPIC_API_KEY` と `CLAUDE_CODE_OAUTH_TOKEN` を入力の値で上書きするので、その 2 つの `env` は資格情報にしない。claude-code-action は入力が空のとき `env` の値を使うので、資格情報にする(2026-11-19 に各 `action.yml` で確かめた)
- `other-secrets` は、エージェントに届く入力、`env`、まるごと式の `env` で見つけた秘密情報のうち、集めたものと同じ名前(大文字と小文字は区別しない)のものを飛ばし、残りの最初のものを数える
- codex は除く。`openai-api-key` の鍵は中継のプロキシにだけ渡り、Codex からは見えない(0015)ので、同じ鍵を `env` などに書くと、エージェントが持たなかった鍵が新たに届く
- 1 つの式に流れ込む秘密情報は、最初の 1 つではなく全てを見る。`secrets.A || secrets.B` の `B` や、`toJSON(env)` の 2 つめ以降の変数の秘密情報も、資格情報の後ろにあれば数える。同じ読み方を、エージェントが持つ秘密情報と、後のステップが使う秘密情報(`agent-code-with-secrets`)にも使う。0015 が `a || b` の両方を見ると決めていたのに、式ごとに最初の 1 つしか見ていなかったため
- エージェントが持つ秘密情報(後のステップで重ねて数えないための一覧、ADR 0028)からも、集めた資格情報を除く。`other-secrets` で数えない資格情報が、後のステップの `agent-code-with-secrets` からも消えないようにするため
- `env` の変数には、値に流れ込む秘密情報を全て結びつける。`${{ env.KEY }}` や `toJSON(env)` で参照したときも、全てを返す。`long-lived-token` は、これまでどおり GitHub のトークンの変数の最初の秘密情報を見る

## 理由

- claude と gemini では、資格情報はもともとエージェントのプロセスの環境変数にある。同じ秘密情報なら、どこに書いてもエージェントが持つ資格情報は増えず、0015 の「自身の資格情報は数えない」と同じ扱いになる
- 2 は名前の付け方しだいで、資格情報でない秘密情報を見逃し、資格情報を数える
- 3 は、MCP サーバーに同じ API キーを渡すよくある書き方を、全て誤検知する

## 受け入れたトレードオフ

- 資格情報の入力にも資格情報の `env` にも渡していない秘密情報は、名前が `GEMINI_API_KEY` でも数える
- 資格情報の入力が `secrets.A || secrets.B` のように複数の秘密情報を流すときは、どれも資格情報とみなす
- 他の秘密情報と同じ値の資格情報を、別の名前の秘密情報に入れているときは見分けられない
