# 0018. SARIF では、同じ規則と位置の結果を 1 つにまとめ、重い方の level と全ての内訳を書く

- ステータス: 承認
- 日付: 2026-11-13

## 文脈

- ADR 0016 は、同じ checkout や秘密情報を複数のエージェントのステップが指すと、同じ位置と規則の結果が複数できることを受け入れた。GitHub は指紋が同じなら 1 つの警告にまとめる、と見込んでいた
- 2026-11-13 に、v0.1.0 の SARIF を GitHub のコードスキャンに送って確かめた。使い捨ての枝に API で送り、確かめた後で解析の記録と枝を消した
  - 重さは、結果の `level` のとおり `error` と `warning` で出た。`security-severity` が無いので、`security_severity_level` は空だった。ADR 0016 の見込みどおり
  - 同じ規則と位置の結果を 2 つ入れると、別々の警告が 2 つできた。2 つに同じ `partialFingerprints` を付けて送っても、2 つのままだった。1 回の送信の中の重複は、GitHub はまとめない
- 重複が起きるのは、ひとつのワークフローの中で、複数のエージェントのステップが同じ場所を指すとき。たとえば、ワークフローの `env` に置いた長く使えるトークンを、2 つの codex のステップが受け取るとき。2 つのステップは、軸の合計が違えば重さも違う
- 平文の出力は、エージェントのステップごとに内訳を書くので、同じ位置の行が複数あっても読み分けられる

## 検討した選択肢

1. SARIF のときだけ、同じファイルの中で規則と位置(行と列)が同じ結果を 1 つにまとめる。level は重い方、message は各ステップの内訳を空行で区切って全て書く
2. 1 と同じで、最初の結果だけを残す
3. まとめずに、結果ごとに違う位置を指すようにする(エージェントのステップの位置を書く)

## 決定

高橋さんが判断を任せ(2026-11-12 に「承認取らなくていい」)、Claude が 1 を選んだ。

- `--format sarif` のとき、ワークフローのファイルごとに、規則の ID と位置(行と列)が同じ結果を 1 つにまとめる。結果の順は、各組が最初に現れた順のまま
- まとめた結果の `level` は、組の中で最も重いもの(`error` が `warning` より重い)
- `message.text` は、各ステップの内訳(平文の 1 行目の文と軸の行)を、現れた順に空行で区切って並べる
- 平文の出力は変えない
- ADR 0016 のトレードオフのうち「GitHub は指紋が同じなら 1 つの警告にまとめる」は事実と違ったので、この ADR で置き換える。ADR 0016 の他の決定はそのまま保つ

## 理由

- 重複した警告は、片方を閉じても、もう片方が開いたまま残る。直す場所は 1 つなのに、警告が 2 つあると、利用者は同じ指摘を 2 回見ることになる
- 最初の結果だけを残すと、後のステップの方が重いときに、重さを軽く見せてしまう(選択肢 2)
- 位置をエージェントのステップに変えると、直すべき場所(checkout やトークンを置いた行)から警告が離れる(選択肢 3)

## 受け入れたトレードオフ

- まとめた警告の message は長くなる。同じ場所を指すステップは、ひとつのワークフローの中で数個なので、読める長さに収まる
- まとめた後の警告では、どのステップが重い方だったかを message の内訳から読む必要がある
- 平文と SARIF で、指摘の数が違うことがある

## 再検討する条件

- まとめた警告の message が長すぎて、GitHub の画面で読みにくいと分かったとき
- GitHub が、1 回の送信の中の重複を指紋でまとめるようになったとき
