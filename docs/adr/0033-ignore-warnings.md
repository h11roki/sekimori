# 0033. 読めない抑える指示と知らない規則の ID は、標準エラー出力に警告する

- ステータス: 承認(`--format github` での出し方は 0035 で足した)
- 日付: 2026-11-15

## 文脈

- ADR 0031 では、`# sekimori: ignore` の打ち間違いを警告せずに読まないとした。レビューで、`ignore[broad-tool]`(s の抜け)や `ignore [broad-tools]` のように見た目が正しい指示が何も抑えず、利用者には CI が止まり続ける理由が分からない、と指摘された
- 警告は、抑える前に指摘のあるステップの `uses:` の行にだけ意味がある。指摘の無いステップの指示は、何も抑えなくても困らない

## 検討した選択肢

1. 抑える前に指摘のあるステップの `uses:` の行で、`sekimori:` で始まる指示が読めないか、知らない規則の ID を含むとき、標準エラー出力に警告する。終了コードと指摘の出力は変えない
2. 1 を SARIF の `invocations` の `toolExecutionNotifications` にも書く
3. 読めない指示を誤りとして、終了コード 2 にする

## 決定

高橋さんが判断を任せ(2026-11-15 に「止まらないで。開発改善を進めて」)、Claude が 1 を選んだ。

- 対象は、コメントを `#` で区切った部分のうち `sekimori:` の後ろが `ignore` で始まるもの(間の空白は問わない)。`sekimori: reviewed by ...` のような理由の文は対象にしない
- 警告は 2 種類
  - `sekimori: ignore[規則, ...]` か、後ろに何も無い `sekimori: ignore` として読めない
  - 括弧の中に、知らない規則の ID がある
- 書き方は `パス:行:列: warning: ...`。位置は `uses:` の行
- 平文の出力のときだけ出す。Action は平文と SARIF で 2 回動かすので、同じ警告がログに 2 回出ないようにする
- 警告は、そのステップに抑える前の指摘があるときだけ出す

## 理由

- 標準エラー出力なら、平文の指摘の出力を変えずに、Action のログに残る
- SARIF の通知(選択肢 2)はコードスキャンの画面に出ないので、見る人が少ない
- 終了コード 2 は読めないファイルのためのもので、打ち間違いで CI の意味が変わると混乱する(選択肢 3)

## 受け入れたトレードオフ

- 指摘の無いステップの読めない指示は警告しない
- `sekimori:` で始まらない打ち間違い(`sekimor: ignore` など)と、`ignore` の綴りの打ち間違い(`ignroe`)は警告しない
- `--format sarif` だけで動かす利用者には警告が出ない
