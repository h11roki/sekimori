# 0021. 公開リポジトリのエージェントのワークフローに sekimori を当て、集計だけを公開する

- ステータス: 承認
- 日付: 2026-11-13

## 文脈

- ADR 0001 は、効き目を費用なしで示せる理由として「公開リポジトリのワークフローに当て、3 つが重なった件数を数えればよい」と書いた。これまで当てたのは、公式の例を中心にした 27 ファイルだけ
- GitHub のコード検索(2026-11-13 に `"uses: <Action>" path:.github/workflows` で数えた)
  - claude-code-action は 23,456 件、codex-action は 1,520 件、run-gemini-cli は 371 件
  - 1 つの問い合わせで返すのは 1,000 件まで。並びは検索の関連度の順で、無作為ではない
  - fork のリポジトリは、既定で検索の対象から外れる
- 当てた結果には、他人のリポジトリで実際に悪用できる設定が含まれうる。名前を出して公開すると、直される前に攻撃の手がかりになる
- 当てる目的は 2 つ。どれだけの割合で 3 つの軸が重なっているかを示すことと、誤検知と見逃しを見つけて規則を直すこと

## 検討した選択肢

1. Action ごとに検索の上位 1,000 件まで集め、sekimori を当てる。結果は件数と割合だけを公開し、リポジトリの名前は載せない。当たった指摘から決まった数を無作為に選び、手で正誤を確かめる
2. 1 と同じで、当たったリポジトリの名前も公開する
3. 名前で選んだ有名なリポジトリだけに当てる

## 決定

高橋さんが判断を任せ(2026-11-13 に「どんどんやっていいよ。承認求めずに」)、Claude が 1 を選んだ。

- 集め方
  - 3 つの Action ごとに、`"uses: <Action>" path:.github/workflows` でコード検索し、100 件ずつ 10 ページまで取る。検索の頻度の上限(1 分に 10 回)を守るため、1 回ごとに 7 秒あける
  - リポジトリとパスで重複を除き、検索が返した blob の SHA で中身を取る
  - 集めたファイルと、集める道具は、リポジトリに入れない。他人のコードで、ライセンスも様々なため
- 当て方
  - その時点の main の sekimori で、ファイルごとに検査する。読めないファイルは数えて、割合の分母から除く
  - 数えるのは、ファイルの数、指摘が 1 件以上あるファイルの数と割合(`error` と `warning` に分けて)、規則ごとの指摘の数、Action ごとの内訳
- 正誤の確かめ
  - 指摘から、乱数の種を決めて 30 件を無作為に選び、ワークフローを読んで、規則の説明どおりの設定があるかを確かめる
  - 誤検知が見つかれば、原因を直す PR を別に出し、直した後の sekimori で数え直す
- 公開
  - 結果は `docs/survey/2026-11.md` に、日本語で書く。件数、割合、正誤の確かめの結果、検索の偏りを書く
  - リポジトリの名前、パス、設定の抜き書きは載せない

## 理由

- 1,000 件ずつでも、3 つの Action を合わせて千件を超え、割合を示すには足りる
- 名前を載せなくても、割合と規則ごとの内訳で、効き目と、どの設定が多いかは伝わる(選択肢 2)
- 有名なリポジトリだけでは、手入れの行き届いたワークフローに偏る(選択肢 3)
- 正誤を確かめないと、件数が誤検知で膨らんでいても分からない

## 受け入れたトレードオフ

- 検索の関連度の順に取るので、無作為の標本ではない。claude-code-action は全体の約 4% しか見ない
- 検索の時点の中身なので、その後に直されたワークフローも数える
- 名前を出さないので、第三者が結果を確かめ直せない。手順と日付を書いて、同じやり方で数え直せるようにする
- 当たったリポジトリの持ち主には、今回は知らせない

## 再検討する条件

- 当たったリポジトリの持ち主に知らせるかを決めるとき
- 規則を足したり変えたりして、数え直すとき
